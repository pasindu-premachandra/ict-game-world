What the design system covers — and the hole in it

From DESIGN.md in the Open Design project, read today. A substring search of the whole design project for “memory” and “adventure” returns nothing.

Covered, build straight to it

  • “Answer option: idle, selected, correct, wrong. Correct and wrong add a tick or a cross and a word.” → mcQuiz
  • “Sort bucket with chips: the bucket under a held chip turns solid.” → sortGame
  • Feedback colours, the lift tokens, the Sinhala type rules, 44px targets, no sideways scroll at 360px

Not designed anywhere

  • A memory / flip-card grid. Not in the component list, not in the showcase, not mentioned. → O2
  • How the bonus set is entered. D3 said “per lesson” but no screen was drawn. → O1

Four decisions

O1

Where do the 18 games live?

The six sets map 1:1 onto grade 9 lessons 1–6, and gate D3 already said “a bonus round per lesson”. Only lesson 7 has no set. Cost of getting it wrong: a child either never finds the bonus games, or the syllabus path gets diluted with content that is not assessed.

O2

The memory game has no design. What should it be?

3 of the 18 games are memoryGame: 5 pairs, 10 cards, flip two and keep them if they match. The design system has no flip-card component and no mention of one. The card faces are text, not icons — “🌡 Temperature” pairs with “Heat detection” — so they need room to read. Mockups are at true phone proportions.

O3

Do bonus scores reach the class leaderboard?

No migration either way: scores is unique on (player_id, grade, activity_id) and the adventure ids (c1, p2) do not collide with the 1.1 ids. So this is purely a product call about what the class board is measuring.

O4

Ship English-first, or wait for the Sinhala?

348 strings have no Sinhala, including every answer option in all 11 quizzes. The fallback works, so nothing breaks either way — the question is whether a mostly-English bonus set in front of a Sinhala student is acceptable in the meantime.

The plan, once those are settled

  1. js/adventure.js — load data/adventure-9.json, list the sets and their three games, route into one. Shape follows O1.
  2. js/activities/mcquiz.js — rounds.js plus an option list, sharing the option-row CSS with trace.
  3. js/activities/sortgame.js — adapt items[] + bins[] into bucket.js's interaction rather than re-implementing it.
  4. js/activities/memory.js — to whatever O2 settles. Skipped entirely if O2 is C.
  5. Scoring: quiz and sort score as their siblings do. Memory scores off moves against a perfect run, so recall earns three stars and brute force does not.
  6. Progress and leaderboard per O3, reusing store.js and leaderboard.js untouched.
  7. sw.js — add every new module to PRECACHE and bump CACHE. The data file is already precached.
  8. Every string through text() and t(), including icon — that was finding F2.

How it gets proven

The same method as the ported types: all 18 games played to completion from their own answer keys, both languages, 375px and 1366px, scores compared against 100, plus deliberately wrong and half-right runs on cleared progress to show the score discriminates. For the memory game specifically, a perfect run must score 100 and a brute-forced run must score less. 0 console messages, 0 horizontal overflow, reduced motion still completable, both gates green, and a read at Sinhala size.

Risk, and it is low. Nothing routes here yet, so a mistake cannot break a screen a child already uses. The real risks are scope and consistency: re-implementing the bucket interaction instead of reusing it, and inventing a memory-card look that does not match a design system nobody has drawn for it. O2 exists so that second one is not decided silently by me.
