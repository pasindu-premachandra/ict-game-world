The move

One builder, two doors into it.

Why 3.4 keeps its row rather than being deleted. check-data.mjs proves extraction is reversible: it rebuilds each language's view out of data/grade-N.json and deep-compares it against the original file. Deleting an activity that exists in the original would fail that gate. Turning it into a link costs nothing and keeps the gate honest.

05

Four decisions

Each one changes what I write. Answer in any order, then send.

Q1Does the builder feed the leaderboard?

This is the one with a database behind it. submit_score() validates every argument (supabase/migrations/0001_init.sql:74-79):

if p_grade is null or p_grade < 6 or p_grade > 9 then
  raise exception 'grade must be between 6 and 9';
end if;
if p_activity is null or p_activity !~ '^[0-9]{1,2}\.[0-9]{1,2}$' then
  raise exception 'activity id must look like 1.2';
end if;

A puzzle id like seq1 is rejected, and a builder that belongs to every grade has no grade to file under. The board is per grade too, since leaderboard_grade groups by s.grade. So anything the builder scores has to land in one grade's table.

Queued. Press Send to Agent once you have answered the rest.

Q2One attempt, or fiddle until the program runs?
Coupled to Q1. If the builder is not scored (Q1 A), fiddling is free and is how a child learns. If it is scored (Q1 B or C), a score everyone reaches by retrying tells you nothing, which is exactly why last session moved the seven ported types to one answer per round.

The original let a child retry until the blocks were right and paid XP with a combo multiplier. Everything built since takes one answer per round, because a retry-until-right score cannot discriminate.

Queued. Press Send to Agent once you have answered the rest.

Q3Does a loop actually hold its blocks?

10 of the 14 programs contain a C-block, a repeat or an if that wraps other blocks. The originals flatten them: the C-block is drawn as an empty C shape and the blocks that belong inside it sit loose underneath, in the right order. The child is never shown a loop containing anything. The design system draws the opposite, with .sbc__body wrapping its children.

07

Risks, and what I am not doing

Risks I can see

  • seq2 is 12 blocks. On a 375px phone that is a long script area plus a tray. The tray scrolls, the script area does not, and I will screenshot it before saying it works.
  • Nesting on a phone (if Q3 is A). A drop target inside a drop target, at 44px minimum, inside 375px. Most likely part to need a second pass.
  • The hub is a fourth kind of screen. The app knows grade picker, lesson path and activity. This adds hub, structure list and program, and the router grows with them.
  • Block text carries HTML (<span class="scratch-pill">, <b>). It is content from the originals, so it gets parsed into structured parts and built with el(). Nothing reaches innerHTML.

Not in this task

  • The 18 adventure mini games. Still no UI, still bonus, still separate.
  • The Sinhala pass over every screen at 375px that came out of the logo finding. Its own job.
  • The grade picker's card shape. The app's square cards diverge from the design system's row cards; I am matching the design system for the new card and leaving the four grade cards alone.
  • The two LiveCheck rows still in Supabase from last session's production check. One line of SQL, but not part of this.
