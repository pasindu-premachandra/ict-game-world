Findings

F1A score earned before the student picks a name is lost for good

pushScore() opens with if (!getPlayer()) return;, so an activity finished before the nickname screen is never sent and never even queued. It stays in igw.progress on the device, which means the star counter in the top bar counts it but the leaderboard cannot.

What the pilot saw Ishini played activity 1.1 first, because the grade picker is the landing screen and nothing asks for a name. She named herself afterwards, when she opened the leaderboard. That first 100 points never reached the server and never will.

500

Both numbers were on screen at the same time. A child who counts their own stars will see the leaderboard owing them a hundred points, and the app gives them no way to understand why.

Why it is not an edge case: the app deliberately does not ask for a name up front, so playing first and naming later is the ordinary path through it. In a lab of thirty students, most would lose their first activity this way.

Why I have not touched it: every fix changes how the app greets a child, and that is a design call rather than a code one. It is decision D1 below.

F2Grade 6 activity 1.3 prints the literal text "[object Object]"

In Pick the Embedded Computer Devices, the "Ceramic plate" option renders [object Object] where its emoji should be. It is on the live site right now, in both languages.

Root cause, and it is two problems stacked The two source files disagree about that distractor. The English original has "Ceramic plate" with a plate icon; the Sinhala original has කෑදර පුටුව, which is a chair, with a chair icon. Because the icons differ, the bilingual merge correctly wrapped the field as {en, si}. It is the only non-string icon in all five data files.

The code half is ours, and it is one line in four places. The renderers pass icon straight into a text node without translating it: js/activities/pick.js:19, js/activities/match.js:18, js/activities/order.js:19 and js/app.js:81. The text() helper at js/i18n.js:82 already handles exactly this shape; the icons simply never got routed through it. This should be fixed whatever happens to the content, because any future icon that differs between the two languages will break the same way and nothing would catch it.

The content half is Ishini and Dilini's. A plate and a chair are not translations of each other, so one of the two originals has the wrong distractor. That is decision D2.

F3A Sinhala spelling slip repeated in the source content

හාවිත appears where භාවිත is meant, in at least the lesson 2 heading and again inside activity 2.1. It is faithful to the original files, so the parity checker will never flag it: the checker proves we copied the content exactly, which is precisely why a typo in the source survives it.

This belongs on the list for Ishini next to the T1 to T5 typos already carried over from the redesign task, rather than being quietly changed here.

Decisions

Three, and only D1 really needs thinking about.

D1What should happen to points earned before a student picks a name?

The tension: asking for a name first protects every point but puts a form in front of a child who just wants to play, and the app was deliberately built the other way round. Letting them play first keeps that, but silently loses work unless we do something with it.

D2The English says a ceramic plate, the Sinhala says a chair. Which is right?

Either works as a distractor, since neither contains an embedded computer. But a child doing the activity in both languages gets a different question, and right now the mismatch is also what puts [object Object] on the screen. I will fix the rendering either way, so no differing icon can ever print as text again. This is only about which word is correct.
